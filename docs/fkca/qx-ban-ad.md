# Quantumult X 去广告基础原理

这篇文章用尽量直白的方式解释 Quantumult X（简称 QX）如何去广告、MITM 解密是什么、规则文件里的 `reject` 和 `redirect` 怎么看，以及广告规则为什么有时会失效。文中的域名和 URL 都是演示用例；实际规则会因 App 版本和订阅更新而变化。

## 总结前置

QX 去广告主要依靠三类操作：拦截独立广告域名、处理独立广告接口、从混合业务数据里移除广告内容。第一种最简单；第二种要匹配正确接口；第三种通常最依赖 MITM 和随 App 变化的脚本。MITM 可以扩大可处理的信息范围，也带来证书与隐私管理责任。规则开着不代表所有广告都能识别，最终效果仍取决于流量是否经过 QX、规则是否匹配、App 是否接受处理后的响应。

## 先记住一句话

QX 会让手机的网络请求经过自己的本地处理流程，再按规则决定放行、拒绝或改写。广告如果来自独立广告服务器，通常可以拦掉请求；广告如果和正常内容混在同一份数据里，就要进一步读取并修改响应。读取 HTTPS 内容时，通常需要 MITM。

## 1. 把 QX 想成网络入口的“门卫”

App 启动时可能会向服务器请求首页内容、图片、登录信息，也可能请求开屏广告。QX 像门口的检查员，看看请求要去哪个域名、是否命中规则，再决定它能不能通过。有些规则还会在服务器回信后检查内容，把广告数据清理掉再交给 App。

![](https://i.postimg.cc/gjYcdpDT/quantumultx-simple-(1).png)

QX 不会自动知道每段内容是不是广告。它依靠规则来识别：规则匹配得上，就能处理；匹配不到，广告就可能照常出现。

## 2. 三种常见广告，以及对应的处理方式

### A. 广告有独立域名

有些 App 把广告请求发给独立的广告域名，例如 `ads.example.com`，正常业务则用其他域名。这时可以按域名拒绝连接。好处是简单，不需要读取 HTTPS 正文；风险是规则误杀了也承载正常图片或接口的域名，App 可能缺图或部分功能异常。

### B. 广告有独立接口，但和业务共用域名

有些 App 的广告请求和首页请求都发往同一个域名，只是 URL 路径不同，例如 `/startup` 用来请求开屏广告，而 `/home` 用来请求首页数据。此时不能轻易拒绝整个域名，否则首页也可能无法加载。更精确的做法是匹配广告接口，拒绝这条请求，或者给 App 返回一个它能接受的“没有广告”的结果。

开屏广告常见这种结构：App 请求启动广告接口；规则让它收到空数据、空列表或本地伪造的响应；App 如果允许没有广告，就继续进入首页。具体 App 也可能在本地缓存广告，或把倒计时写在 App 逻辑里，所以规则不一定能完全消除开屏画面。

### C. 广告混在正常内容里

信息流广告可能和普通文章、回答或商品放在同一个 JSON 响应中。此时整条请求不能简单拦掉，否则普通内容也会消失。规则需要读取响应，识别广告卡片，再把相应项目从列表里移除。这类方式依赖 App 接口字段，App 更新后字段一变，脚本就可能失效。

## 3. QX 的配置文件都在管什么

配置文件看起来很长，但通常分成几类工作：

- **分流规则（Filter）**：按域名、IP 等特征决定请求直连、走代理，或拒绝连接。广告域名列表通常在这里发挥作用。
- **重写规则（Rewrite）**：按 URL 匹配请求，拒绝请求、重定向，或修改请求/响应的头部和正文。
- **MITM 设置**：决定哪些 HTTPS 域名允许由 QX 解密，以便规则查看 URL 路径或响应正文。
- **远程订阅（Remote）**：从外部地址下载并更新分流或重写规则。主配置里常见的是订阅地址、开关、标签和更新间隔，具体匹配细节则在订阅内容里。
- **策略组（Policy）**：决定流量走直连还是某个代理节点。它影响请求的网络出口，不等于广告规则本身。

一些第三方规则需要转换成 QX 能识别的格式，配置中的 `resource_parser_url` 和 `opt-parser` 可能承担资源解析工作。是否需要解析取决于订阅文件格式；原生 QX 配置不一定需要解析器。

## 4. 什么是 MITM？它如何解密 HTTPS？

HTTPS 可以想成 App 和网站之间的加密信封。正常情况下，App 与网站建立加密连接，传输途中的普通网络设备看不到信封里的内容。启用 MITM 后，QX 在允许处理的域名上分别和 App、网站建立连接：

```text
App  ⇄  Quantumult X  ⇄  真正的网站
```

大致步骤如下：

1. App 发出 HTTPS 请求，请求经过 QX。
2. 对列入 MITM 范围的域名，QX 向 App 出示一张由 QX 本地根证书签发的证书。
3. 如果设备已安装并信任 QX 根证书，且 App 接受这张证书，QX 就可以在本地解开这段连接。
4. QX 再与真正的网站通信。若重写规则命中，QX 可以读取或修改相应内容，然后把结果交回 App。

这不代表 QX 会自动解密手机上的所有 HTTPS。是否处理取决于域名是否在 MITM 范围内、证书是否被信任，以及 App 是否接受被替换的证书。采用证书固定（Certificate Pinning）的 App 会额外核对服务器证书，可能因此拒绝连接。QX 官方示例说明，MITM 只处理主机名范围内的 TLS 连接。[1]

### MITM 相关词语

- **证书 / 根证书**：用于证明通信对象身份的凭证。MITM 需要设备信任 QX 的本地根证书，QX 才能向 App 出示由它签发的目标网站证书。
- **hostname（主机名）**：域名，例如 `api.example.com`。MITM 主机名范围决定哪些 HTTPS 连接可被处理。配置里以 `-` 开头的名称通常表示排除项。
- **SNI**：HTTPS 握手时客户端提供的目标域名信息，常用于在内容尚未解密时识别连接目标。
- **证书固定**：App 除了信任系统证书，还要求证书与 App 预设值相符。QX 的证书可能无法通过这种检查。
- **QUIC / HTTP/3**：基于 UDP 的传输方式。常见 HTTPS MITM 重写主要处理可被 QX 捕获和解密的 TLS 连接；如果 App 走了不适合该规则的传输路径，规则可能看不到需要的内容。丢弃部分 UDP/QUIC 流量有时会促使 App 改用其他连接方式，但也可能造成卡顿或联网异常，并不保证一定回退成功。

## 5. `reject` 和 `redirect` 规则怎么读

下面的 `example.com` 仅为示例，不是你配置中的真实广告域名。

### 按域名拒绝连接

```ini
[filter_local]
host, ad.example.com, reject
```

这条分流规则表示：匹配到 `ad.example.com` 的请求使用 `reject` 策略。远程广告规则也可以列出很多待匹配域名，再统一指定拒绝策略。

### 按 URL 拒绝请求

```ini
[rewrite_local]
^https?://ad\.example\.com/.* url reject
```

这是重写规则，按 URL 匹配后拒绝请求。QX 官方示例中，`reject` 会返回无内容的 404；如果 App 需要成功状态或特定数据格式，也可以考虑其他拒绝响应形式，例如：

```ini
[rewrite_local]
^https?://api\.example\.com/start url reject-200
^https?://api\.example\.com/adlist url reject-array
```

常见形式包括 `reject-200`（返回 200 空响应）、`reject-dict`（返回空 JSON 对象 `{}`）、`reject-array`（返回空 JSON 数组 `[]`），以及 `reject-img`（返回一张 1 像素图片）。用哪一种取决于 App 预期的数据格式；用错了也可能导致报错或页面异常。[1]

### 把请求重定向到另一个 URL

```ini
[rewrite_local]
^https?://go\.example\.com/promo url 302 https://www.example.com/home
```

这表示匹配到旧地址后，QX 返回 302 重定向，让客户端改去访问新 URL。QX 官方配置示例也展示了 `307` 重定向。[1] `reject` 是让请求被拒绝或收到指定空响应；`302` / `307` 则是告诉客户端去另一个地址。

### 改写服务器响应内容

例如服务器返回的 JSON 中有广告列表，规则可把列表改为空数组。下面只展示规则的概念，真实响应字段和格式必须与 App 接口一致：

```ini
[rewrite_local]
^https?://api\.example\.com/start url response-body "ads":\[.+\],"next" response-body "ads":[],"next"
```

如果是 HTTPS 且需要匹配加密 URL 的具体路径或响应正文，通常还需要相应域名启用 MITM。QX 官方文档展示了响应正文替换及 JavaScript 响应处理示例。[2]

**注意：分流层的拒绝和重写层的拒绝是不同写法。**前者按网络目标决定请求去向；后者按 URL 规则生成拒绝响应。若某个请求需要读取服务器响应再改写，就不能让该请求在建立有效响应之前被直接切断。

## 6. 结合你上传的配置看

根据你提供的 `QuantumultX.conf`：

- `[filter_remote]` 第 263 行加载 Cats-Team 的广告规则，并设置 `force-policy=reject`。这让规则集中命中的目标走拒绝策略，主要属于按域名或规则匹配拦截。
- `[rewrite_remote]` 第 189 行启用了“墨鱼去开屏2.0”远程订阅。主配置只给出订阅地址，没有写出每个 App 的 URL 和响应处理细节。因此，不能只凭主文件确认某个 App 的开屏是被拒绝、返回空数据，还是以其他方式处理。
- `[rewrite_remote]` 第 191 行启用了知乎净化 JavaScript，并设为 `opt-parser=true`。这表明它是远程脚本类型资源，具体处理方式要看脚本和解析后的重写规则。
- `[mitm]` 行中设置了 `skip_validating_cert = true`。这是跳过相关证书验证的配置项，可能降低证书校验保护；不清楚作用范围时，不建议无必要启用。
- `hostname` 行里列出的项目带有 `-` 排除标记，主配置本身没有在该行列出正向 MITM 域名。远程资源或 QX 的当前生效设置可能影响实际范围，建议在 App 中核对当前 MITM 主机名和证书状态。
- 配置还启用了 `udp_drop_list = 443, STUN, QUIC`。这不是广告识别规则；它会影响相应 UDP 流量，可能促使部分 App 改用其他传输方式，也可能影响淘宝、QQ 等 App 的连接表现。

远程订阅是会变化的。订阅地址、规则名称和更新时间并不能代替查看当前规则正文。启用第三方规则前，应确认来源可信，并定期检查是否仍适配自己的 App。

## 7. 为什么规则开着，广告还在？

可以按下面顺序排查：

1. **请求有没有经过 QX？**确认 QX 隧道已启用，并检查相关流量是否被配置排除、直连模式或其他设置绕开。
2. **规则是否启用且更新成功？**确认订阅状态正常；规则过旧或下载失败时，匹配表可能不完整。
3. **规则属于哪一类？**独立域名广告可尝试域名拦截；独立接口适合 URL 规则；与内容混在一起的广告需要处理响应正文。
4. **MITM 条件是否满足？**若规则需要查看 HTTPS 路径或正文，核对证书是否受信任、主机名是否在范围内，以及 App 是否使用证书固定。
5. **是不是传输路径或缓存造成？**QUIC/UDP 可能影响特定改写方式；App 本地缓存也可能让旧广告继续显示。清缓存或重装是否有效，取决于 App 和规则说明。
6. **接口是否变化？**App 更新可能改变 URL、JSON 字段或广告标记，脚本需要随之更新。某些商业推广也长得像普通内容，规则可能选择保守放行，避免误删正常内容。

## 8. 隐私风险怎么理解

MITM 能让 QX 看到被纳入处理范围的 HTTPS 请求和响应，所以相关流量可能包含登录状态、请求参数或个人信息。风险大小取决于 MITM 覆盖范围、规则脚本来源、设备日志和备份管理，以及证书是否妥善保管。

Quantumult X 的隐私政策称，启用时捕获的数据和配置保存在设备上；开发者不会访问这些数据，除非用户通过分享功能主动分享。[3] 第三方订阅则由各自维护者提供，是否值得信任需要单独判断。远程脚本应按代码和规则看待，启用前应确认来源，不要把证书文件、口令或敏感日志随意分享。

更稳妥的习惯包括：只对必要域名启用 MITM；不用时关闭相关处理或移除不再需要的证书；谨慎对待跳过证书校验的选项；避免安装来源不明的配置和脚本。

## 9. 新手词汇速查：这些东西如何接力工作

词汇放在一起看，就像一条从“规则准备”到“请求处理”的流水线。下面以 App 启动时请求开屏广告为例：

```text
准备规则：
Remote 远程订阅下载规则
  → enabled=true 表示启用
  → update-interval=86400 表示大约每天更新

实际请求：
App 请求开屏广告
  → TUN / 本地 VPN 把请求交给 QX
  → Filter / 分流检查域名和目标
      ├─ 命中广告域名 + reject：请求在这里被拦下
      └─ 允许继续：选择 direct 或 Policy 策略组决定网络出口
  → 如果规则需要查看 HTTPS 路径或正文：MITM 在允许范围内解密
  → Rewrite / 重写按 URL 匹配并处理请求或响应
  → QX 把正常或处理后的结果交回 App
```

这条流程里，每个词承担不同的一段工作：**Remote 负责把规则带进来；TUN 负责让请求经过 QX；Filter 负责判断请求往哪里去；Policy 负责选择出口；MITM 在需要时打开 HTTPS 内容；Rewrite 按接口规则处理内容；最后 App 根据收到的结果显示页面。**

同一个广告请求不一定会经过每一个环节。例如，Filter 用 `reject` 拦下广告域名后，请求不会到广告服务器；这时就没有服务器响应可供 Rewrite 清理。相反，如果要改的是服务器返回的 JSON，网络请求必须能正常到达服务器，且 HTTPS 响应必须能被 MITM 解密。若只匹配域名并拒绝连接，通常不需要 MITM。

### 两种常见配合方式

**独立广告域名：**`TUN → Filter 匹配广告域名 → reject`。这条路径短，不必拆 HTTPS 信封。误把业务域名或共用 CDN 拦掉，可能连正常图片或功能也一起影响。

**混在业务数据里的广告：**`TUN → Filter 放行请求 → Policy 选出口 → MITM 解密指定 HTTPS 域名 → Rewrite 匹配接口 → 从 JSON 列表里删除广告项 → App 显示剩余内容`。这一条依赖更多条件：域名在 MITM 范围内、证书受信任、App 接受证书、接口字段仍符合脚本预期。

### 词汇放回流程里理解

- **TUN / 本地 VPN**：请求的入口通道。QX 隧道没启用，或流量绕开它，后续规则就无从处理。
- **Remote / 远程订阅**：规则的来源。远程资源更新后，设备可以获得新规则；订阅地址只负责提供规则，不代表规则一定匹配当前 App。
- **`enabled=true`**：订阅资源或规则是否启用。关闭后，该资源不会按预期参与处理。
- **`update-interval=86400`**：以秒计的更新间隔，86400 秒约为一天。它影响规则新旧，不改变规则本身的匹配逻辑。
- **Filter / 分流**：请求到达 QX 后的一道判断关口，主要根据域名、IP 等特征决定拒绝、直连或交给策略组。它通常不解析 JSON 正文。
- **`reject`**：拒绝匹配到的请求。若是 Filter 里的 `reject`，连接被拦截；若是 Rewrite 里的 `url reject`，QX 可按重写规则给出拒绝响应，具体表现不同。
- **`force-policy=reject`**：给远程分流列表指定统一的处理去向。命中该列表的请求交给 `reject` 策略。
- **`direct`**：请求直连目标，不经代理节点。它仍可由 QX 规则管理；直连不等于绕开 QX。
- **Policy / 策略组**：Filter 决定请求要走代理时，Policy 再选择具体节点或线路。它管网络出口，不负责识别广告内容。
- **MITM**：处理 HTTPS 内容时用到的本地解密环节。只有匹配到 MITM 主机名、设备信任证书、App 接受该证书且连接方式可处理时，QX 才能读取相应内容。
- **Rewrite / 重写**：按 URL 或规则处理请求与响应，可以拒绝、重定向、改请求头或修改响应正文。重写规则若要改 HTTPS 正文，通常需要 MITM 条件成立。
- **JSON / 字段**：App 接口常用的数据格式。JSON 像一个带标签的盒子，字段是盒子里的名称，例如 `ads`、`items`；脚本根据这些字段找到广告条目并修改。
- **CDN**：分发图片、视频等内容的服务器网络。广告素材和正常素材可能共用 CDN，因此 Filter 按 CDN 域名拦截时要小心误伤。
